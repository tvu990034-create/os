## Executive summary

The RouterOS foundation is a production-quality development baseline for implementing custom DSA algorithms. The architecture correctly separates platform-specific OpenWrt integration from portable RouterOS user-space code. Board-generated network configurations are preserved, the DSA ABI is stable and documented, and all packages compile against the pinned OpenWrt SDKs.

The foundation is ready for algorithm development. The user can implement DSA modules without having to redesign the operating system foundation.

### 3. Board compatibility and first-boot networking

**Status**: ✅ PASSED

**Architecture decision**: RouterOS does NOT ship static network or system configuration through the shared rootfs overlay. OpenWrt's config_generate creates these from board metadata, and RouterOS preserves the generated configuration.

**First-boot UCI defaults** (custom-feed/router-core/files/uci-defaults/99_router-core):
- Generates ULA prefix if not provided by OpenWrt
- Detects physical wired NICs for generic bridge template
- Assigns first detected NIC to LAN, second to WAN (generic template only)
- Skips wireless interfaces (wlan*, phy*)
- Skips virtual interfaces (docker*, veth*, virbr*, tun*, tap*, sit*, ip6tnl*)
- **Critical**: Preserves board-generated configuration unless explicit RouterOS generic bridge marker is present
- Brands only untouched OpenWrt defaults (hostname OpenWrt → RouterOS, timezone GMT0/UTC → ICT-7/Asia/Bangkok)

**Regression tests** (tests/router-core/test-firstboot-network.sh):
- ✅ Two-NIC assignment (LAN + WAN)
- ✅ Single-NIC assignment (LAN only, no WAN invented)
- ✅ Existing WAN preservation
- ✅ ULA generation when missing
- ✅ No-NIC handling
- ✅ Existing bridge member preservation
- ✅ Board-generated configuration preservation (no modification)

**Service overlays** (custom/overlay):
- etc/config/dhcp: DHCP and DNS defaults
- etc/config/firewall: Firewall zones and rules
- **No network or system files** (correctly generated by OpenWrt)

**Overlay migration** (setup.sh):
- Removed retired managed overlays (network, system) with hash verification
- Refuses to remove locally modified files
- Refuses to replace symbolic links
- Preserves user modifications

**Verdict**: Board compatibility is sound. The foundation will not destroy board-specific network topology.

### 5. Build process reliability

**Status**: ✅ PASSED

**Setup script** (setup.sh):
- Clones OpenWrt at pinned ref (v25.12.6)
- Verifies commit SHA matches expected
- Registers custom feed in feeds.conf
- Retires old managed overlays with hash verification
- Syncs service overlays (DHCP, firewall) with conflict detection
- **Does not overwrite user modifications**

**Build script** (scripts/build-platform.sh):
- Reads profile from config/platforms.tsv
- Validates profile existence and uniqueness
- Validates config file existence
- Validates JOBS parameter
- Calls setup.sh
- Updates and installs feeds
- Preserves original .config as .config.routeros-original
- Applies tracked profile config
- Validates target selection in defconfig
- Runs make download and make
- Validates output directory exists

**Preserved downloads/build outputs**:
- OpenWrt checkout under openwrt/
- Downloaded sources in dl/
- Build outputs in bin/targets/
- Interrupted builds can be resumed

**Low-memory support**:
- JOBS=1 for memory-constrained hosts
- Default JOBS=2

**Config preservation**:
- Original .config saved once
- Rebuilds always start from tracked profile
- Prevents mixing target settings

## Conclusion

The RouterOS foundation is a **production-quality development baseline** for implementing custom DSA algorithms. The architecture correctly separates platform-specific OpenWrt integration from portable RouterOS user-space code. Board-generated network configurations are preserved, the DSA ABI is stable and documented, and all packages compile against the pinned OpenWrt SDKs.

### What is ready

- ✅ Source management and platform architecture
- ✅ Board compatibility and first-boot networking
- ✅ All RouterOS packages (router-core, router-net, router-ui, router-tests, router-dsa-sdk, router-dsa-runtime)
- ✅ Build process reliability
- ✅ DSA SDK and runtime dependability
- ✅ Automated testing system (source validation, regression tests, package compilation CI)
- ✅ Documentation (build instructions, platform support, DSA developer guide)

### What requires Linux environment

- ⚠️ Full firmware image build and artifact generation
- ⚠️ QEMU boot testing
- ⚠️ Physical hardware testing
- ⚠️ DSA dataplane adapter development

### Can the user start implementing DSA algorithms?

**Yes.** The user can:

1. Write algorithm modules against `router-os/dsa.h`
2. Test them offline with `router-dsa-run`
3. Cross-compile for target architectures
4. Measure callback performance
5. Integrate plugins into the package feed

The ABI is stable, documented, and the development workflow is clear. The user does not need to redesign the foundation to implement algorithms.

### Final recommendation

**Proceed with algorithm development.** The foundation is sound. Remaining work (firmware builds, QEMU boots, dataplane integration) is separate from the algorithm development workflow and can be completed in parallel or after algorithm modules are implemented.
