## Important architectural decisions

### 1. Board-generated configuration is preserved

RouterOS does not ship static network or system configuration through the shared rootfs overlay. OpenWrt's config_generate creates these from board metadata, and RouterOS preserves the generated configuration. This ensures that board-specific Ethernet names, switch ports, and VLAN topology are not destroyed.

### 2. Generic bridge assignment is opt-in

The first-boot script only assigns ports to a generic bridge if an explicit RouterOS marker is present. Board-generated configurations are left entirely unchanged. This prevents RouterOS from breaking device-specific network topology.

### 3. Platform profiles are based on OpenWrt targets, not CPU architecture

Support is based on actual OpenWrt device targets and profiles, not just CPU architecture names. A device is not supported merely because its CPU architecture is supported.

### 4. DSA runtime is offline testing only

The current runtime executes plugins against synthetic packet metadata. It is not a live packet dataplane. A separate dataplane adapter is required before plugin decisions can affect traffic.

### 5. Only trusted plugins should be loaded

The runtime does not sandbox plugins or restrict their system calls. Only load shared objects from trusted sources. Future work may add signature verification.

### 6. Read-only management UI

The LuCI dashboard has a read-only RPC ACL. It can display system status and network information but cannot modify configuration. This preserves the secure separation between diagnostics and operations.

## DSA ABI and algorithm implementation

### ABI version

Current version: 1

Entry point: `router_dsa_get_algorithm_v1`

Header: `custom-feed/router-dsa-sdk/files/include/router-os/dsa.h`

### How to implement a new module

1. **Create a plugin directory**:
   ```bash
   mkdir my-algorithm
   cd my-algorithm
   ```

2. **Write the plugin** (my-algorithm.c):
   ```c
   #include <router-os/dsa.h>

   static int my_init(struct router_dsa_context *context) {
       // Initialize plugin state
       context->userdata = NULL; // or allocate private state
       return 0;
   }

   static int my_process(struct router_dsa_context *context,
                         const struct router_dsa_packet *packet,
                         struct router_dsa_decision *decision) {
       // Examine packet metadata
       // Fill in decision
       decision->actions = ROUTER_DSA_ACTION_SET_MARK;
       decision->mark = 1234;
       return 0;
   }

   static void my_destroy(struct router_dsa_context *context) {
       // Clean up resources
   }

   static const struct router_dsa_algorithm algorithm = {
       .abi_version = ROUTER_DSA_ABI_VERSION,
       .struct_size = sizeof(algorithm),
       .name = "my-algorithm",
       .version = "1.0.0",
       .stage = ROUTER_DSA_STAGE_CLASSIFY,
       .capabilities = 0,
       .init = my_init,
       .process = my_process,
       .destroy = my_destroy,
   };

   ROUTER_DSA_PLUGIN_EXPORT
   const struct router_dsa_algorithm *
   router_dsa_get_algorithm_v1(uint32_t requested_abi_version) {
       if (requested_abi_version != ROUTER_DSA_ABI_VERSION)
           return NULL;
       return &algorithm;
   }
   ```

3. **Create a Makefile**:
   ```makefile
   CC ?= cc
   CFLAGS ?= -O2
   TARGET := my-algorithm.so
   SOURCE := my-algorithm.c
   ABI_INCLUDE := ../custom-feed/router-dsa-sdk/files/include

   all: $(TARGET)

   $(TARGET): $(SOURCE) $(ABI_INCLUDE)/router-os/dsa.h
       $(CC) $(CFLAGS) -std=c11 -Wall -Wextra -Werror -fPIC -shared \
           -I$(ABI_INCLUDE) -o $@ $(SOURCE)

   clean:
       rm -f $(TARGET)
   ```

4. **Build and test on host**:
   ```bash
   make
   router-dsa-run my-algorithm.so --ingress 3 --length 128 --ip-version 4 --protocol 6
   ```

5. **Cross-compile for target**:
   ```bash
   make clean
   make CC=x86_64-openwrt-linux-musl-gcc
   ```

6. **Measure performance**:
   ```bash
   router-dsa-run my-algorithm.so --ingress 3 --length 128 --ip-version 4 --protocol 6 \
       --iterations 1000000 --warmup 10000
   ```

7. **Validate ABI compatibility**:
   - Set struct_size to sizeof() for all structures
   - Check abi_version matches expected
   - Return NULL for unsupported ABI versions

### ABI contract

- **Packet metadata**: Immutable for the duration of process()
- **Decision output**: Fill in actions and corresponding fields
- **Context**: Use userdata for plugin-private state
- **Callbacks**: init() once, process() per packet, destroy() once
- **Error handling**: Return non-zero on failure
- **Memory ownership**: Plugin owns userdata; host owns packet/decision

### Security

Only load trusted shared objects. The runtime does not sandbox plugins. A malicious plugin can read/write arbitrary memory, execute arbitrary code, connect to the network, or modify files.

### Future dataplane integration

The current runtime is for offline testing only. To integrate a plugin into the actual packet forwarding path, a dataplane adapter must be written that:

1. Intercepts packets at a Linux hook point (XDP, tc, netfilter)
2. Extracts metadata matching the packet structure
3. Calls the plugin process() callback
4. Applies the decision actions
5. Ensures thread safety if the plugin claims ROUTER_DSA_CAP_THREAD_SAFE
6. Handles plugin failures gracefully

This adapter does not yet exist.

## Can you begin implementing DSA algorithms?

**Yes.**

The foundation is stable, documented, and ready for algorithm development. You can:

1. Write algorithm modules against `router-os/dsa.h`
2. Test them offline with `router-dsa-run`
3. Cross-compile for target architectures
4. Measure callback performance
5. Integrate plugins into the package feed

The ABI is stable (version 1), the development workflow is clear, and the foundation will not require redesign as you implement algorithms.

### What you don't need to do

- Redesign the operating system foundation
- Modify OpenWrt or the Linux kernel
- Implement DPDK or XDP optimizations
- Build a new dashboard
- Change the networking stack
- Fix package dependencies
- Resolve build system issues

### What you should focus on

- Implementing your DSA algorithms
- Testing them with the offline runtime
- Measuring their performance
- Documenting their decision logic

### What remains for later

- Firmware image builds (require Linux environment)
- QEMU boot testing (require Linux environment)
- Physical hardware testing (require actual devices)
- DSA dataplane adapter (future work)
